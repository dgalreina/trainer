# Élite Trainer

App personal para registrar la evolución en el gym, con IA que guía al usuario.
Primero PWA para uso propio; después App Store (iPhone). Si funciona, se podría monetizar.

## Estructura (monorepo con npm workspaces)

- `apps/mobile`: Expo + React Native + TypeScript + Expo Router. Se prueba como PWA (`expo start --web`) y más adelante como app iOS.
- `apps/api`: backend Node + TypeScript con NestJS (ESM). Se despliega como contenedor en AWS ECS Fargate detrás de API Gateway (región UE). `src/main.ts` arranca el servidor (local y en el contenedor); `src/lambda.ts` es el handler de Lambda del CRUD, ya sin uso (queda de referencia para el agente de IA).
- `packages/shared`: tipos y validaciones compartidos (contrato de la API).

## Decisiones tomadas

- **Frontend estático:** `expo export --platform web` con `output: "static"`. Se publica en GitHub Pages u hosting estático. Si va en una subruta, configurar `experiments.baseUrl`.
- **Los datos viven en el backend** (MongoDB Atlas), nunca solo en el dispositivo: Safari puede borrar el almacenamiento local de una PWA.
- **La API key de Anthropic solo en el backend.** Nunca en el cliente.
- **IA con Claude** (Sonnet para análisis comparativos y de fotos, Haiku si basta). Aislar el proveedor tras funciones propias, por ejemplo `analyzeProgress(photos)`.
- **Control de coste:** guardar `userId` y tokens consumidos en cada llamada a la IA; `max_tokens` limitado; contexto mínimo (resúmenes, no historial completo); límite de gasto mensual en la consola de Anthropic y alerta de facturación en AWS Budgets.
- **Lo específico de iOS** (pasos y energía activa de HealthKit, suscripciones con RevenueCat) va detrás de una capa propia (`getSteps()`, etc.). En web devuelve vacío o entrada manual.
- **Dieta:** el cálculo de calorías y macros lo hace el código (Mifflin-St Jeor, energía activa), no la IA. La IA solo explica y adapta. Topes duros en código: sin déficits agresivos ni calorías por debajo de un mínimo seguro.
- **Fotos de progreso:** la IA habla de indicios y tendencias, sin juicios estéticos. Consentimiento explícito, almacenamiento privado y cifrado, posibilidad de borrarlas (datos de salud, RGPD).
- **Región UE** para todo lo que guarde datos.
- **Login con Amazon Cognito** (email y contraseña, user pool en la UE). No guardamos contraseñas. La app habla con Cognito por `fetch` directo (`apps/mobile/src/lib/cognito.ts`, sin SDK: mismo código en web, iOS y Android); solo se guarda el refresh token (SecureStore en el móvil, localStorage en la web). La API valida el access token con un guard global (`aws-jwt-verify`) y usa el `sub` como `userId`. Más adelante se podrá añadir Apple/Google.
- **Entrenos:** `Routine` es la plantilla (lo planeado) y `WorkoutSession` lo realizado. Los ejercicios del catálogo base tienen `ownerId` nulo; los de usuario llevan su `userId` y se archivan en vez de borrarse.

## Backend en AWS (decidido)

- **La API normal (CRUD) corre en un servidor siempre encendido: ECS Fargate** (una tarea de 0,25 vCPU y 0,5 GB), con la misma app NestJS en un contenedor. Se probó antes en Lambda y se abandonó: la cuenta de AWS limita Lambda a **10 ejecuciones simultáneas** (compartidas con el resto de proyectos) y al arrancar la app salían ráfagas de peticiones que pasaban de 10, con 5xx en el cliente; además cada arranque en frío tardaba ~1,7 s. La versión con Lambda está guardada en la etiqueta de git `version-lambda`.
- **Lambda queda reservada para el agente de IA** (trabajos puntuales y pesados: análisis de fotos, resúmenes, chat). Todavía no existe. No borrar `src/lambda.ts`, `build:lambda` ni `@codegenie/serverless-express` sin pensar en ello: son la base de ese handler.
- **Límites de cuenta (cuenta nueva):** App Runner no deja crear servicios («can't create new App Runner services») y Lightsail Containers da «maximum limit of Lightsail Container Services»; por eso se eligió ECS. Si algún día falla un despliegue con un mensaje de límite, es cosa de la cuenta, no del código.
- **Chat con la IA en streaming:** handler de Lambda aparte (junto al agente, como máximo 2 funciones). Node soporta streaming de forma nativa en Lambda (`awslambda.streamifyResponse`); Python no. Las Function URLs con streaming no funcionan dentro de una VPC, y si el cliente se desconecta la función sigue ejecutándose y cobrando. Pendiente de confirmar: si API Gateway (REST o HTTP) soporta el streaming. Mientras tanto se puede empezar sin streaming (respuesta completa).
- **Empaquetado (resuelto):** `npm run build:lambda --workspace apps/api` compila con tsc y copia el JS con sus dependencias de producción a `apps/api/lambda-dist`. No se usa esbuild: no emite los metadatos de los decoradores y además rompe `mongoose` con `@nestjs/mongoose` ("Cannot set property nextConnectionId").
- **Infraestructura con AWS CDK** en `apps/infra` (stack `TrainerStack`, eu-west-1): VPC con subredes públicas y sin NAT (un NAT cuesta ~33 $/mes), clúster ECS con un servicio Fargate, Cloud Map (el API Gateway localiza la tarea por un VPC Link, sin balanceador, que costaría ~17 $/mes) y un API Gateway HTTP con tope de 50 peticiones/s, más el presupuesto mensual de 10 $ (coste real ~14 $/mes, cubierto por créditos de AWS mientras duren). La imagen es `apps/api/Dockerfile` (contexto: la raíz del repo; reutiliza `build:lambda` para empaquetar) y CDK la construye y la sube a ECR al desplegar, así que hace falta **Docker Desktop abierto**. Desplegar: `npx cdk deploy` dentro de `apps/infra`. La URI de Mongo vive en SSM (`/trainer/mongodb-uri`, SecureString) y llega al contenedor como secreto de ECS. La URL pública sale como `ServerApiUrl` y está en `apps/mobile/src/config.ts`. Atlas (M0) permite `0.0.0.0/0` porque la tarea no tiene IP fija: pasar a PrivateLink antes de abrir la app al público.
- **Catálogo base de ejercicios:** `apps/api/seed/exercises.base.json` (147: los 134 de antes, 4 para la plantilla «Pre-competición» y 9 para las de «Fuerza máxima» e «Hipertrofia»; 4 añadidos para la plantilla «Pre-competición») y `npm run seed --workspace apps/api` para cargarlo (idempotente).
- **Web:** GitHub Pages en https://dgalreina.github.io/trainer/ (workflow `.github/workflows/pages.yml`).
- En el servidor Mongoose mantiene su propia conexión; en una Lambda (agente) reutilizarla entre invocaciones (variable fuera del handler).
- **Cada dato se pide una vez al back y se comparte entre pantallas** con un proveedor (`ExercisesProvider`, `FoodsProvider`, `TrainingsProvider`…), nunca con hooks que cada pantalla instancia por su cuenta.
- Alerta de facturación en AWS Budgets desde el primer día.

## Orden de trabajo

1. Registro de entrenos (ejercicio, series, repeticiones, peso) con backend y login básico.
2. Endpoint de IA: analizar las últimas semanas y sugerir la próxima sesión.
3. Fotos de progreso con análisis.
4. Dieta y, al pasar a iOS, pasos de Salud.

## Visión del producto

- **La IA es un entrenador personal omnipresente, dedicado solo al cuerpo del usuario.** No es una función suelta que opina tras un entreno: conoce todo su historial, su estado físico, su peso cada vez que lo registra, lo que come y lo que anda, y sus mejoras. Todo lo que registra la app es información para ese entrenador.
- **Modelo de entreno:** un **Entrenamiento** (por ejemplo "Fuerza") tiene nombre, fecha de inicio y duración en semanas, y contiene las **rutinas** de cada día ("Pecho + Espalda", "Pierna"...). Las rutinas no existen sueltas: viven dentro de un entrenamiento (con id propio, porque las sesiones apuntan a ellas). La semana en curso se calcula con `trainingProgress` (`packages/shared`), por días de calendario y sin horas. El usuario marca cuál es su entrenamiento **actual** (y, más adelante, su dieta actual) en `/me/settings`; "Hoy" lo muestra arriba y ofrece sus rutinas. El catálogo de ejercicios se abre desde Yo > Mi cuenta (no aparece en Entrenamientos), ya no es una pestaña.
- **El descanso entre series es de cada rutina** (`restSeconds` en `Routine`: Sin, 60, 90, 120 o 180 s; 90 por defecto). Se elige en el editor de la rutina y no se cambia durante el entreno. Las rutinas anteriores heredan el descanso que tenía su entrenamiento (el campo antiguo sigue en Mongo solo para eso). Ojo con Zod: un `.default()` dentro de un `.partial()` rellena el campo ausente y machaca el valor guardado al editar; por eso crear y editar comparten los campos sin valores por defecto (`trainingFields` en `packages/shared/src/training.ts`, `routineFields` en `routine.ts`).
- **Rutinas: «Día 1», «Día 2»… no es el nombre**, es la posición dentro del entrenamiento (`dayLabel`, `routineTitle` en `packages/shared`). El nombre es opcional ("Pecho + Espalda"). «Nuevo entrenamiento» abre la misma pantalla que editar (`/entrenamiento/nuevo`, `lib/new-training.ts`) con el formulario en blanco y **sin crear nada**: el nombre es obligatorio y no hay nombre por defecto, así que el entrenamiento se crea en cuanto se escribe uno (fecha de hoy y 8 semanas por defecto; si se sale sin nombre no queda nada). Las semanas se cambian con − y +. El entrenamiento **actual** ya no se marca dentro de la pantalla: en la lista de Entrenos cada tarjeta lleva arriba a la derecha un punto que, al pulsarlo, se rellena y lo marca como actual (pulsar fuera del punto abre el entrenamiento). El **+** crea la siguiente rutina; los datos del entrenamiento (nombre, fecha, semanas) se guardan solos, sin botón. En esa pantalla solo se crean y listan los días (Día 1, Día 2…; ✕ si están vacías); al tocar uno se abre su página «Editar rutina» (`screens/routine-editor.tsx`), donde **todo se hace en la misma página, sin salir** (`components/routine-form.tsx`, al estilo de zitytraining, donde lo que aquí es «rutina» se llama «entrenamiento»): nombre opcional, buscador de ejercicios en línea (tolerante: ignora «de», «con», el orden y una letra de diferencia; si no existe, se ofrece crearlo) y un botón de cuatro cuadraditos que abre un selector a pantalla completa con los ejercicios por grupo muscular en cuadrícula (`components/exercise-picker.tsx`; cada recuadro lleva su ilustración si la tiene, y se mueven (alternando las dos posiciones con un fundido) como mucho 4 a la vez: las primeras que se ven ENTERAS en pantalla, que cambian al hacer scroll (se miden con onLayout del grupo, la cuadrícula y cada recuadro), `components/exercise-motion.tsx`; recuadros blancos con filo fino salmón; la lista usa `components/fading-scroll.tsx`: difuminado arriba y abajo solo si hay más contenido por ese lado, válido solo sobre fondo liso, no sobre las ondas), columnas S1…Sn con reps y kg, técnica (SS/RP/DESC), nota y descanso propio por ejercicio, asa de tres rayas para reordenar arrastrando en vertical, descanso y un hueco libre al final. Se guarda solo (700 ms tras el último cambio); «Borrar rutina» al final. Pendiente: notas por ejercicio y desplazamiento automático de la página al arrastrar cerca del borde.
- **Ejercicios de una rutina: técnica, nota y descanso propio (hecho):** cada slot lleva `technique` (`ss` superserie, `rp` rest-pause, `desc` descendente; excluyentes, ausente = serie normal; sustituye a los antiguos `linkedToNext`/`restPause`, que se siguen leyendo en Mongo y se traducen con `legacyTechnique`, también en borradores guardados en el dispositivo y en sesiones), `notes` (máx. 500) y `restSeconds` opcional (ausente = el de la rutina). En el editor: chips SS · RP · DESC · Nota · Descanso (la nota y las opciones de descanso se despliegan al pulsar). En el entreno se ve la nota, la técnica y el descanso propio; el temporizador usa el del ejercicio y, en una superserie, solo salta al acabar el último ejercicio de la cadena (con **su** descanso). Los rangos de repeticiones («8-12») no tienen campo: se escriben como repeticiones por serie, 12-10-8-8. Siguiente: plantillas de entrenamiento (la hoja de «Pre competición» de ejemplo).
- **Plantillas de entrenamiento (hecho):** entrenamientos de ejemplo compartidos por todos (colección `training_templates`, de solo lectura desde la app, cargados con `npm run seed --workspace apps/api` desde `apps/api/seed/training-templates.base.json`, idempotente por `key`; el seed falla si un ejercicio no está en el catálogo base). Los ejercicios van **por nombre**, no por id, y se traducen al usar la plantilla; no llevan pesos. API: `GET /training-templates` y `POST /training-templates/:id/use` (`{ startDate }`; copia a los entrenos del usuario con técnica, descanso, notas y repeticiones, y devuelve el entrenamiento). En Entrenos > Plantillas hay una tarjeta por plantilla con «Usar esta plantilla» (`TemplateCard`; las plantillas viven en `TrainingsProvider`). Primera: **Pre-competición** (hoja de enero de 2017: 5 días de 12-10-8-8 al fallo, descanso 1' y 2' en pierna; «+» de la hoja = superserie; prensa 20-30-40-50; extensiones en 3 series descendentes; 8 semanas por defecto porque la hoja no lo dice; «Abdomen» solo está en el nombre de las rutinas porque la hoja no lista ejercicios de core). Otras dos, de los PDFs de J. M. Galisteo: **Fuerza máxima (volumen SS)** y **Hipertrofia (verano 2017)** (5 días cada una, 8 semanas por defecto porque no lo dicen; el abdomen, que el PDF de fuerza dice que son 2 días aparte, no se incluye). Cómo se leen sus notaciones: `2x15, 4x8-12` = 2 series de 15 + 4 de 12-10-8-8; un intervalo `a-b` se reparte de más a menos repeticiones (`8-12` → 12-10-8-8, `10-12` → 12-11-10-10, `6-8` → 8-7-6-6); `4x10+10` = superserie de dos ejercicios; `2x10+10+10 (serie descendente)` = 2 series DESC; `6xfallo` = 6 series sin repeticiones y nota «Al fallo»; en la de hipertrofia el descanso es de 2' y cada ejercicio lleva la nota «Las 2 últimas series al fallo, muy pesadas». Equivalencias: jaca = sentadilla hack, remo en punta = remo en T, pájaros en contractor = elevación posterior en máquina, multipower = máquina Smith. Pendiente: plantillas de dietas (hay un PDF «Dieta Carga/Descarga», L-V y S-D, que tendría que ser dos dietas porque la app no varía por día de la semana).
- **Scroll y pantallas apiladas:** el título (y `fixedTop`) van fijos y solo el contenido se desplaza; sin barras de scroll visibles (`global.css`). Las pantallas apiladas no llevan la barra de pestañas (se descartó mostrarla en todas): más espacio, con la flecha para volver. Llevan flecha «atrás» dibujada (`BackButton`, prop `onBack` de `Screen`) y el título centrado.
- **Sin títulos en las pestañas** (ahorrar espacio): Hoy lleva «¿Qué vas a entrenar hoy?» a la altura del círculo del entrenamiento actual; Entrenos y Dietas llevan arriba, fijos, **Mis entrenos / Plantillas** y **Mis dietas / Plantillas** (`components/section-tabs.tsx`; Yo usa el mismo componente). Las plantillas (compartidas por todos los usuarios, con `ownerId` vacío como los ejercicios base, y una acción «Usar» que copie a lo propio) están por hacer: de momento solo un texto. Las pantallas con `fade` (Yo, Entrenos, Dietas) tienen los botones fijos y el contenido con difuminado en los bordes (`FadingScroll mask`: máscara CSS, vale sobre las ondas).
- **Pestañas y «Yo»:** las pestañas son Hoy · Calendario · Entrenos · Dietas · Yo (Cuenta ya no es pestaña; Yo va la última). «Yo» tiene dos botones: **Mis datos** y **Mi cuenta** (sesión, modo claro, catálogo de ejercicios, cerrar sesión; `components/account-section.tsx`). **Calendario** es su propia pestaña (`screens/calendar.tsx`) (los días en un scroll continuo, cada uno con las horas de arriba abajo, con cada entreno y cada pesada a su hora (ver «Calendario del día»); se mueven con pulsación larga y arrastre vertical del círculo, con ajuste a 5 min, y se guarda con `PATCH /sessions/:id` o `PATCH /me/weights/:id`; las comidas se añadirán con la dieta; es la base de la gráfica de ondas) y **Mis datos** (nombre, fecha de nacimiento, sexo, altura, nivel de actividad, objetivo y notas/lesiones para el entrenador; el peso no es un campo suelto sino un registro de pesadas con fecha y hora). API: `/me/profile` (GET y PUT parcial; `null` borra un dato), `/me/weights` (rango `from`/`to`, `latest`, alta y baja) y `/sessions?from=&to=`. Todos los datos para calcular calorías (Mifflin-St Jeor) salen de aquí. Las fechas y horas viajan en ISO 8601 y el día de calendario se calcula con la hora del dispositivo.
- **Calendario del día (hecho):** la dieta es la **plantilla** fija y cada día tiene sus **instancias**. Las comidas de la dieta aparecen en el día desde que se activa (`dietOn`) y **cuentan en «Comido este día» salvo que se editen o quiten**. Se pueden mover (asa ≡), editar (lápiz) y borrar (dentro del editor) y eso **solo afecta a ese día**: se crea un `MealLog` con `dietMealId` (la comida de la dieta de la que viene) y, si se borra, otro con `skipped: true` (sin alimentos, no cuenta ni se muestra, solo evita que reaparezca); la dieta no se toca. Los botones «Registrar comida/peso» ya no existen: **tocar un hueco vacío del día** abre «Añadir a las HH:MM» (cuartos de hora) con Comida, Peso o Entrenamiento (este abre la pantalla del entreno con `?at=` = esa hora como inicio). Las ventanas son `Sheet`; el editor de comida es `components/meal-editor.tsx`. **Gráficas del día** (`components/day-energy-chart.tsx`, cálculo en `packages/shared/src/energy.ts`, hecho por el código): una línea vertical central (el cero) y, detrás de las tarjetas (semitransparentes), **azul a la izquierda = gasto**, **rosa a la derecha = lo comido** y **amarillo anaranjado (`amber`) = balance acumulado** desde las 00:00. Gasto = basal (Mifflin-St Jeor de `calculateTargets`, último peso y edad de hoy) repartido en 96 tramos de 15 min + cada entreno terminado (MET 5, solo lo que excede del basal: orientativo, no medimos calorías quemadas; un entreno en curso no cuenta). Cada comida se reparte en 30 min. Gasto y consumo comparten escala (tasas); el balance tiene la suya. Sin datos del perfil solo se dibuja el consumo y se avisa. Opacidad: lo ya pasado 50 %, lo que aún no 20 % (hoy desde la hora actual; días futuros enteros). Las cifras (gasto, consumo y balance, «previsto a las 24:00» si el día no ha acabado) van en el resumen de abajo, no al tocar la gráfica. **Calendario en scroll continuo y a pantalla completa:** los días van uno debajo de otro en un scroll continuo (`DayList` en `components/day-timeline.tsx`: una `FlatList` de unos 2 años a cada lado de hoy, cada día con altura fija de 24 h = 1344 px, así solo se pintan los días cercanos y los datos al llegar no mueven nada). Cada día empieza a las **00:00 para todos** (se descartó un ajuste de «cuándo empieza mi día»: con el scroll continuo la madrugada simplemente sigue al día anterior) con una pequeña tarjeta «Día X» (la fecha; «· Hoy» en hoy) y, debajo, marcas discretas («Comienza la dieta…», «Comienza el entrenamiento…»; solo se guarda el día, no la hora, así que van al principio). No hay cabecera de fecha ni flechas: la fecha va en la tarjeta de cada día y en la de abajo (`Mié 11 · 702 kcal`); un botón «Hoy ↑/↓» aparece solo cuando hoy no está a la vista. **El día que se muestra** es el del centro de la zona visible: de él habla la tarjeta de abajo y de él cuelga qué semanas se cargan (`useWeekEvents(mondayOf(día))`, ventana de 5 semanas que se recarga al cambiar de semana). Lo que se hace desde un hueco (añadir comida, peso o entreno) es del día de ese hueco, no del que muestra la tarjeta. La línea de tiempo y las gráficas pasan por detrás de la barra de pestañas (`Screen fullBleed`; sin difuminado) y de la tarjeta de abajo, que flota encima. En esta pestaña **no hay ondas**: al entrar suben fuera de la pantalla con una transición de 750 ms hasta desaparecer (y dejan de pintarse), y al ir a otra pestaña bajan de nuevo (marca `noWaves` en `lib/tabs.ts`; la hace el navegador con una transición CSS de `transform`, no un temporizador por fotograma, que competía con la animación de las propias ondas y iba a saltos): en la web las pone `(tabs)/_layout.tsx` en un componente aparte (`TabsWaves`, para no repintar las cinco pestañas a cada fotograma) y en nativo cada pantalla, con `Screen noWaves` en el calendario. **Resumen de abajo** (`components/meal-log-section.tsx`, flota sobre la gráfica, que llega hasta el borde de abajo): cerrado son dos líneas (las calorías y «Déficit/Mantenimiento/Superávit · ±N kcal») con una flecha; al abrirlo se desglosa en proteínas, hidratos y grasas y se leen objetivo, gasto y balance; y siempre debajo una **barra de balance** (`components/balance-bar.tsx`) que dice si vas en déficit, mantenimiento o superávit según `balanceZone` (`packages/shared/src/energy.ts`: mantenimiento = balance dentro de ±5 % del gasto del día, mínimo ±100 kcal; con «previsto» si el día no ha acabado). Pendiente: pasos y energía activa de Salud (iOS).
- **Eventos del calendario como círculos (hecho):** comidas, pesadas y entrenos son círculos pequeños (64 px) apoyados en el margen izquierdo, sobre la gráfica (`EventCircle`, `placeCircles` en `components/day-timeline.tsx`; los que se pisan en vertical van a carriles hacia la derecha): nombre y debajo kcal o kg (los entrenos terminados llevan las kcal gastadas estimadas, «~N kcal» = `workoutExtraKcal`, y «En curso» si no han terminado; sin número de series). **Tocar**: comida abre su editor, pesada abre `WeighInSheet` en modo edición (kg, hora y «Borrar pesada»), entreno en curso abre su pantalla y los terminados no hacen nada (irán a un historial). **Pulsación larga (350 ms) + vibración y arrastre vertical** para cambiar la hora (se guarda con ajuste a 5 min); un gesto rápido es scroll. La vibración usa `Vibration.vibrate`: funciona en Android y no en iOS web (Safari no la ofrece); en la app nativa irá con `expo-haptics` (Haptic Touch). Al soltar se cancela el clic fantasma del navegador (si no, cerraba al instante la ventana recién abierta). **Las gráficas siguen al círculo mientras se arrastra:** `EventCircle` avisa (`onDrag`, solo al cambiar la hora ajustada) y `DayList` pasa esa vista previa (`DragPreview`) al día afectado, cuyo `modelOf(day, preview)` recalcula `dayEnergy` con el evento ya movido; la tarjeta de abajo solo se actualiza al soltar. Hay un **difuminado suave arriba**, justo bajo la barra de pestañas (máscara CSS en `DayList`).
- **Catálogo de alimentos (hecho):** igual que el de ejercicios pero con macros. Un `Food` guarda kcal, proteína, hidratos y grasa **por 100 g** más porciones caseras; las macros de una cantidad las calcula siempre el código (`foodMacros`, `sumMacros` en `packages/shared/src/food.ts`), nunca la IA. Base de 320 alimentos, con una categoría «Suplementos» (batidos, whey/ISO 90, caseína, creatina, BCAA, EAA, arginina…; los aminoácidos cuentan ~4 kcal/g como proteína y la creatina 0; no hay campo aparte: se registran como cualquier alimento; si más adelante se quiere un checklist diario de suplementos, será una función propia) (los 119 primeros, 183 añadidos después y el caqui: quesos Philadelphia, pavo, conejo, pescados, fiambres, frutas, dulces, salsas…) en `apps/api/seed/foods.base.json` (valores orientativos de tablas habituales, pendientes de revisar), cargados con `npm run seed --workspace apps/api` (idempotente; también carga los ejercicios). API `/foods` (listar con `q`, crear, editar, archivar); un nombre repetido da 409 (no se devuelve el existente como en ejercicios, porque las macros pueden diferir). Pantalla en `/alimentos`, desde Dieta. Siguiente: dieta manual (comidas con hora y alimentos con gramos), el registro de lo comido en el calendario, y más tarde la IA que traduce texto libre a alimentos del catálogo. Las comidas referencian alimentos por id: al editar uno, cambian sus macros pasadas (si molesta, guardar una copia de las macros en cada comida registrada).
- **Dieta (primera versión hecha):** una `Diet` tiene nombre, objetivo (`GOALS`) y fecha de inicio, y dentro las **comidas** (`Meal`: nombre, hora "HH:MM" y alimentos con gramos; con id propio, el registro de lo comido apuntará a ellas). API `/diets` (CRUD) y `/diets/:id/meals` (alta, edición y baja; cada operación devuelve la dieta completa, con las comidas por hora). La dieta actual se marca en `/me/settings` (`activeDietId`, validado; se desactiva al borrarla). Pantallas: lista en la pestaña Dieta y detalle en `/mi-dieta/[id]` (`screens/diet-editor.tsx`, comidas en `components/meal-card.tsx`, con buscador de alimentos y cantidad en gramos o por porción). **El objetivo diario no se guarda: lo calcula `calculateTargets` (packages/shared/src/diet.ts) con los datos de «Yo» y el último peso:** Mifflin-St Jeor × factor de actividad; ajuste -15 % / 0 / +10 % según objetivo; topes duros (déficit máximo del 25 %, nunca por debajo de 1200 kcal mujer / 1500 hombre ni del metabolismo basal, y proteína máx. 35 % de las calorías); proteína por kg según objetivo, grasa 25 % y el resto hidratos. Si faltan datos del perfil, la pantalla dice cuáles. **Registro de lo comido (hecho):** `MealLog` (colección `meal_logs`) es lo realizado, como `WorkoutSession`; la dieta es lo planeado. Cada alimento guarda **una copia de sus macros al registrarlo** (las calcula el servidor con `foodMacros`), así que editar un alimento del catálogo no cambia lo ya comido. API `/me/meals` (rango `from`/`to`, alta, edición y baja; mover la hora no recalcula nada). En «Yo»: las comidas salen en el calendario (salmón = ingesta; los entrenos son azul cielo = gasto, token `skySoft`) y se arrastran como lo demás; debajo, `MealLogSection` con el total comido frente al objetivo, la lista del día y «Registrar comida», que puede empezar desde una comida de la dieta actual. **Pendiente:** mostrar la dieta actual en «Hoy», editar una comida ya registrada (hoy se borra y se vuelve a crear), y la IA.
- **Pantalla principal ("Hoy"):** el usuario elige qué entrena hoy (Pecho, Hombro, Espalda...); al tocarlo se abre el entreno del día, donde ve y modifica pesos y repeticiones, con botón "Comenzar" arriba, "Finalizar" abajo y un temporizador de descanso opcional entre series. Al finalizar, la IA da su opinión sobre cómo ha ido.
- **Sin entrenamiento asignado**, la pantalla principal invita a hablar con la IA para que genere uno según las necesidades del usuario.
- **Cómo encaja con las decisiones técnicas** (al construirlo):
  - El contexto de la IA sigue siendo mínimo: un resumen compacto y mantenido por el código del estado del usuario (objetivos, lesiones, tendencias) más herramientas (tool use) para consultar datos concretos bajo demanda, en vez de volcar el historial en cada llamada.
  - Lo que la IA genera (rutinas, ajustes) sale como datos estructurados validados con los esquemas de `packages/shared` y usando ejercicios del catálogo por id; nunca texto libre que la app tenga que interpretar.
  - Los cálculos de calorías y macros siguen en código; los topes de seguridad no dependen de la IA. No da consejo médico.
  - Guardar siempre `userId` y tokens por llamada, y `max_tokens` limitado.
- **El entreno en curso se guarda como borrador en el dispositivo** (el gimnasio implica bloquear el móvil o cambiar de app). El temporizador de descanso se calcula con la hora de fin, no con una cuenta atrás: iOS suspende las PWA en segundo plano. Hoy vive en `lib/workout-draft.ts` y se guarda con `lib/storage.ts`: en la web va a localStorage; en iOS/Android SecureStore se queda corto (límite de ~2 KB por valor), así que al hacer la app nativa hay que pasar el borrador a un almacenamiento de ficheros (por ejemplo `expo-file-system`). El aviso de fin de descanso (vibración y pitido) solo funciona con la app abierta y en primer plano.

## Diseño

- **App luminosa:** predomina el blanco. El color de la app es el **rosa-salmón** (acción principal, ingesta); el naranja solo en último caso; el azul cielo y el azul verdoso son acentos y se reservan sobre todo para el gasto de calorías. Limpio y minimalista. Tokens en `constants/theme.ts`, nunca colores sueltos en las pantallas; la paleta fina se afinará más adelante. Texto sobre salmón en oscuro, y `primaryText` (salmón más profundo) para texto y enlaces, porque el salmón base no tiene contraste sobre blanco.
- **Las ondas son el motivo principal** de la identidad visual: anchas, redondeadas, con degradado y dominadas por el salmón y el rosa (componente `Waves`). El azul solo asoma como un matiz aparte que se desvanece: mezclado con el salmón en el degradado sale un malva grisáceo. En modo oscuro se atenúan a la mitad.
- **Visión de la pantalla del día (hecha en lo esencial, ver «Calendario del día»; el naranja del balance es ahora el amarillo anaranjado `amber`):** calendario con las horas de arriba abajo y los eventos marcados (comida, entreno...). Detrás, una gráfica de ondas superpuestas sobre la línea del 0 de calorías, en el centro:
  - **Azul (gasto):** metabolismo basal (banda tenue constante), pasos y entrenos. Hacia la izquierda.
  - **Rosa (ingesta):** cada comida es un bulto en su hora. Hacia la derecha.
  - **Naranja, por detrás (balance acumulado del día):** cruza la línea del 0; cada comida lo empuja al rosa y el gasto al azul.
  - Cuidado al implementarlo: las tasas por hora y el acumulado tienen escalas muy distintas (normalizarlas por separado y dar los números al tocar una hora); el acumulado va como línea fina con relleno suave para que no se confunda con el rosa; por la mañana el acumulado siempre irá hacia el azul antes de comer, así que conviene marcar el objetivo del día y dibujar el resto del día más tenue, como proyección.
  - Requiere hora en cada comida y entreno. Pasos y energía activa vendrán de Salud en iOS; antes, entrada manual. El basal lo calcula el código (Mifflin-St Jeor).
- **Logo e iconos:** fondo casi blanco, ondas translúcidas en la parte baja (los colores de la app: cielo desvaneciéndose, melocotón, rosa y salmón, que se mezclan donde se cruzan) y una É redondeada en degradado salmón-rosa encima (nombre: "Élite Trainer"). El diseño es código: `apps/mobile/scripts/generate-logo.py` escribe los SVG en `assets/branding/` y renderiza con Chrome todos los PNG (`assets/images/icon.png`, `favicon.png` y, en `public/`, los iconos de la PWA, el de iOS y el maskable). Admite una variante con la É en gris oscuro (`generate-logo.py dark`). Descartado: ondas intensas por todo el cuadrado con azules fuertes (parecía de playa), y ondas opacas sobre fondo salmón (translúcidas se mezclaban en tonos apagados; el fondo casi blanco lo resuelve).
- **Implementación prevista:** `react-native-svg` (funciona igual en web e iOS) con `linearGradient` y curvas suaves; animaciones con Reanimated. Los datos del balance salen del código (Mifflin-St Jeor, energía activa), no de la IA.
